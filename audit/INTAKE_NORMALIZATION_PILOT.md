# Existing-intake normalization — Stage 133

2026-10-19. Isolated pure server-side mapping helper. Disabled by default, no live service import, migration, new route or command.

The normalizer reads the actual activity-intake shape: id, student actor ID, revision, state and content programme/semester/course/type. It uses the existing identity-grant adapter's freshly evaluated output and verified personMap to find exactly one current institutional roster student. Actor IDs such as s1 are never assumed to equal MIS student IDs. The current institutional identity/roster/masters must be approved, versioned and valid at server time. Input is trusted server-loaded source data; this function does not authenticate, verify cryptographic provenance or import MIS records.

Only an explicit server-stored teamInitiation opt-in is recognized: enabled, routing kind, team version and, for same-batch academic projects, an approved course-offering reference. No opt-in is created by this step. Legacy intakes remain on their current workflow. SAME_BATCH_ACADEMIC is valid only for Project intake type and requires exact programme label mapping, a single chosen offering, lead's roster programme/batch/semester/course membership and matching existing semester/course labels. There is no fuzzy text match or guessed batch. MULTIDISCIPLINARY_RESEARCH is valid only for Research type and maps the lead's programme; it does not force the research group into the lead's batch/course. Multidisciplinarity and group acceptance remain the routing helper's checks.

The output is a detached minimum proposal descriptor and source/version mapping: intake ID/revision, team case/version, verified actor/person/student references, identity authority version, roster/master/programme/offering references and academic scope. Purpose, outputs, names, fee data, contact details and private narrative are neither copied nor hashed. expectedMapping can reject changed references before a later save. Approved-source immutability, CAS, fresh authorization and reviewer permission checks remain the future loader/save responsibilities.

No approval authority is inferred from these academic mappings. The source adapter still needs explicit grants and one configured final-approval policy. The existing live engine, sessions, demo account switcher, intakes, notifications, club records and database schema are unchanged. This checkpoint does not connect the normalizer to the isolated save loader's earlier teamPilotSource fixture contract; that is the next bounded step.
