# Stage 173 — Controlled assigned-mentor responses

## Essential change and workflow impact

Add `respondIntakeTeamMentor` to the existing dedicated team dispatcher and authenticated workspace endpoint. The current assigned mentor can accept after declaring no unresolved conflict and capacity to supervise, or request reassignment with a reason. Both outcomes update the existing assignment record's response/state; they do not create a replacement, change the frozen proposal, complete consultation, grant final approval or permit execution. No SQL migration, new module, provider, account, role grant or ordinary engine command permission is introduced. The request step remains separate from the response.

The existing mentor request source validation is extracted into a shared server-only function in its current file. Request and response now use exactly the same current approved MENTOR_ASSIGN authority, PROJECT_MENTOR eligibility, institutional/kind/academic scope, verified actor-to-person mapping, active-person checks and independence checks. This avoids duplicate business rules while retaining existing request behavior. The original assigner must remain verified, active and authorized; the mentor must remain verified, active and eligible. Missing, expired, revoked, unavailable or conflicting sources deny the response rather than treating the stored snapshot as current authority.

The response additionally requires the latest unique REQUESTED assignment ID/version, no previous response or withdrawal, the current reviewed handoff/submission, and exact equality between the original assignment source snapshot/basis and the rebuilt current snapshot. The requesting account must resolve to the same stable person as the assigned mentor. A second verified alias of that person can respond; another person or a demo role cannot. The snapshot binds the first-review version, submitted digest, frozen team versions, source/normalization references, route binding and explicit assignment/eligibility references. The original request's expertise, capacity, reason, authorship and source basis are retained.

Acceptance requires `noConflict:true`, representing the existing conflict/capacity acceptance declaration. Reassignment requests use `noConflict:false` and cannot claim acceptance. Blank, oversized or control-character feedback, forged extra fields and invalid decisions are rejected. Both outcomes record the current responder actor, timestamp and reason. There is one response per request; duplicate or contrary decisions require the future controlled replacement process.

Fresh trusted sources are loaded twice and compared before the existing atomic workspace revision compare-and-swap and structured audit insert. Failed audit writes roll back; concurrent writes preserve the winner without a losing response. The audit references the existing INTAKE_MENTOR_ASSIGNMENT version and decision reason without copying feedback or capacity narrative. The student workspace retains only the existing minimal assignment ID/version/mentor/state summary. Private response details and institutional source bindings are not added to that projection. Generic demo mentor mutations remain blocked for team cases.
