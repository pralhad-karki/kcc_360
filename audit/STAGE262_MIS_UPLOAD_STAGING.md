## Completed code

- Reused the existing pinned SheetJS 0.20.3 parser and existing ZIP/workbook structural checks. The existing plan reader exposes its internal parse function; plan behavior is unchanged. A CommonJS packaging copy retains the exact vendor bytes and licence and is integrity-tested against the retained manifest. No new parser download or invented MIS export field.
- Added strict UTF-8 CSV byte decoding and bounded XLSX-to-CSV translation, feeding Stage261's existing normalized student validator. Explicit mapping uses actual column names supplied by staff; no vendor mapping is presumed. One worksheet is auto-selected only if it is the sole sheet; multiple sheets require an explicit visible selection. Mapped XLSX cells must be text, including stable IDs and ISO dates/timestamps. Numeric IDs/dates are rejected rather than silently reformatted. Unmapped numeric columns may remain numeric. Formulas, hyperlinks, merged/hidden selected layouts and unsupported cells are rejected. Existing archive size/expansion/active-content structural checks apply; antivirus is not connected.
- Added institution-scoped private upload staging through the existing D1 workspace/audit tables and R2 binding, separate from both owner demo data and normalized student data. No schema migration or automatic production ledger provisioning. The future approved provider must supply both provisioned private ledger rows.
- Persisted `STAGING` reservation plus audit before R2 writes. Original bytes go to a server-generated private key, with SHA-256/size. `AVAILABLE` plus audit is recorded only after a successful write. Interrupted writes remain explicitly STAGING, visible in the owner's authorized recovery listing, and may be retried with the same operation and bytes or purged. They cannot be read or committed. No partial student import occurs.
- Private reads recheck current institution/source/uploader/person authority and expiry, verify stored size and SHA-256, and decode the original stored bytes again. Preview includes original-byte provenance. Commit reuses the existing confirmation, identity matching, stale-data, idempotence and atomic student-save path, with an additional staging revision fence in the transaction. A concurrent staging mutation/purge prevents the commit.
- Commit reports retain original source filename/hash/size/MIME/upload time/uploader/decoder/sheet and normalized CSV hash separately. `originalFileRetained` describes evidence retained **at commit**; current retention state is resolved through the staged file ID and purge ledger, not by rewriting historical reports. Existing reports without provenance remain valid and are unchanged.
- Explicit purge tombstones the stage before deleting R2 bytes. Failed deletion remains PURGE_PENDING and retryable; successful deletion is audited as PURGED. Purge does not remove imported student records, reports or historical learning records. A late write observed after purge is deleted and cannot finalize; purge retry also attempts deletion for PURGED records. Cleanup errors explicitly require retry by file ID.
- Added reusable authenticated HTTP service for bounded multipart upload, authorized recovery listing/preview, JSON commit and purge. Same-origin/custom-header guards, strict command/form fields, metadata/file-name agreement and pre-body staff authorization apply when configured. The actual new `/api/mis-imports` route preserves existing owner-only authentication and is **disabled by default**: GET returns no-store unavailable status, POST returns503 without reading the body or accessing the DB.

## Authorization and activation boundary

No institutional staff provider or approved storage policy has been supplied. The protected API therefore does not accept real exports yet. Request JSON, an owner demo persona, an email or a role label cannot activate it. `createMISUploadService` accepts only server composition, requiring an approved trusted-context loader, DB/R2 stores and pinned parser. That loader must establish current verified subject/person, source/institution permission, expiry and authorization fence. Storage configuration must include an approved policy version and staging TTL (supported bound60–86400seconds); no actual institutional retention duration has been chosen.

Expiry blocks preview/commit automatically. Physical purge is an explicit authorized operation; no automatic retention scheduler or institution-wide cleanup job has been installed. Deployment must remain inactive until the operational retention/recovery policy and approved provider composition are installed. R2 and SQL are not one distributed transaction: the audited staging/purge states make interrupted cross-store operations visible and retryable. A cleanup failure must be resolved through purge retry; no claim of distributed atomic file storage is made.

The HTTP seam is implemented and tested, but there is no new staff upload UI in this checkpoint. A full error-resolution/reconciliation interface, mapping editor, ledger provisioning, larger-volume indexed history migration, academic-structure/enrollment/faculty imports and local-progression reconciliation remain pending. Imported master data still creates no passwords, sessions, roles or automatic local progression.
