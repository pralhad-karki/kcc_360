# Team-lead search and selection interface — Stage 139

Activity Intake now renders a lead-side search entry only for a server-projected intakeTeamAccess capability with explicit leadProposals (proposal ID/version, lead student ID, current team revision). No production source currently supplies that capability. Runtime remains disabled and no live directory or membership has been enabled. Capability display never substitutes for server authorization.

The browser controller calls only searchIntakeTeamStudents through the existing endpoint. It checks matching account, workspace/proposal versions, response discriminator, unique bounded rows and pagination. Results retain only the seven approved display fields and use escaped text/DOM listeners. The lead is not selectable as another member. Names or IDs are searched with bounded queries; previous/next pages use the same query. Selection is deduplicated across pages/queries, with removal controls, and limited to the existing command bound of 99 other students (100 including lead). This is an input bound, not an adopted institutional team-size rule.

Selections are temporary memory only. No invitation, membership, enrolment, notification or workspace save occurs. A changed returned student version removes that old selection; errors clear all results/selections and require review. Stale account/revision, capability loss, navigation or a closed/replaced modal prevents late results from rendering. A small optional applyShared cleanup hook clears invitation/lead UI on any refreshed workspace/persona response, preventing old scoped selection data persisting in the modal. Existing synchronization behavior otherwise stays unchanged.

The UI explains that selection has not sent invitations and every invitee must accept. Invitation preparation/revision controls are the next step. Trusted source installation, capability discovery, explicit intake opt-in and authority provision remain prerequisites for activation; current legacy routing and forms are not migrated or redesigned.
