# Lead invitation confirmation — Stage 140

The existing lead search/selection modal now contains a separate confirmation form, only when the current server-owned lead capability explicitly grants canPrepareInvitations and selects a consistent invitationAction (CREATE with teamRevision 0, or REVISE with a positive revision). Current production does not supply this capability or a trusted loader; the runtime remains disabled. Display capability is not authorization: the existing server normalizes the actual intake and checks identity, lead grant, roster, academic sources, revisions and atomic save independently.

The form previews the lead and complete selected list, requires an unchecked explicit confirmation, and prepares invitations only after submission. Search submission remains separate. No student is accepted on another person's behalf. For replacement rounds the warning states that prior history is retained and all other students must accept afresh; prior acceptance is not carried forward. The UI does not manufacture a next team version, update intake metadata or bypass the server's requirement for a valid newly authorized round/source.

Only proposalId, expectedTeamRevision and memberIds (lead plus unique selected IDs) are sent alongside the existing account/workspace revision and Activity Intake context. Raw identity, grants, roster rows, names and client configuration are not sent. Save acknowledgement must match action/account/proposal and expected workspace/team revision increments. Only a fresh full workspace response may replace workspace data. Temporary selections close/clear on success, conflict, malformed acknowledgement or uncertain save. There is no automatic retry/replay. If the save was acknowledged but refresh failed, the message explicitly says the invitations were saved and requires review before retrying. Notification dispatch/delivery is not claimed.
