# Team invitation recipient interface — Stage 137

The existing Activity Intake overview now has an optional own-invitation panel, rendered only for an explicit server workspace projection `intakeTeamAccess: {enabled:true, proposalIds:[...]}`. The current server does not provision this capability and the invitation runtime remains disabled; therefore no live controls or invitations are enabled by this step. This capability is a UI discovery contract, never authorization: every command remains subject to independent server checks.

The separate browser controller reads the dedicated INTAKE_TEAM_COMMAND response and shows only the recipient's latest invitation. It uses the actual ownInvitation structure, escapes titles/references and offers only server-projected Accept, Decline or Withdraw actions. Buttons use DOM listeners, not project content inside inline handlers. No directory, peer invitation or historical round is exposed. Invitation reads never replace the workspace data; successful writes require a fresh full workspace GET with matching account and adequate revision before applying it. Account/revision changes discard stale responses. Conflicts are not replayed and errors require refresh/review. No client roster, grants, identity or enabled configuration is sent.

Existing intake forms, submission/routing, engine commands, permissions, SQL structures and API routes are preserved. The engine receives only a harmless optional rendering hook, with no browser controller imported into server execution. The new browser file is copied by the existing preparation process. No new module or dependency is introduced.

Automated evidence: check-intake-team-client.mjs exercises the actual controller in a VM with fixture responses: default-hidden state; reference filtering; actual own-response shape; escaping; stale-account/wrong-actor rejection; workspace preservation; controlled write/full-refresh sequencing; conflict without replay. Existing command-route, command-bridge, project-resource-policy, sync, activity-intake and role-dashboard suites plus TypeScript are rerun. Previous 119-suite baseline belongs to Stage 136, not a new complete baseline. Browser/keyboard/institutional acceptance remains Not run.
