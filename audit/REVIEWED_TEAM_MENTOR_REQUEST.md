# Stage 172 — Controlled mentor request for reviewed teams

## Essential change, reuse and impact

Connect a current reviewed institutional team intake to the existing `mentorAssignments` history with one REQUESTED record. Add `requestIntakeTeamMentor` to the existing dedicated dispatcher on the existing authenticated workspace endpoint. No SQL migration, new module, engine command permission, provider, real role grant or automatic mentor acceptance is introduced. Complexity is moderate because the existing mentor functions authorize fixed demo accounts and require legacy ROUTING_CONFIRMED records; calling them directly or fabricating that routing state would bypass the institutional team boundary.

Reuse the current frozen-submission/source/route validator through a server-only `validateReviewedTeamSource` function. It validates the reviewed source, not the caller's permission. The new command independently requires exactly one current scoped MENTOR_ASSIGN assignment held by the requesting verified active person. This authority may differ from the first reviewer: the Academic Coordinator can request the mentor after subject-faculty review if the approved authority source explicitly assigns that capability. A first reviewer, final approver, role label or student preference alone grants no assignment right.

The selected mentor must map from the requested actor ID to a verified stable person with exactly one approved, current, available scoped PROJECT_MENTOR eligibility assignment. For same-batch academic work both assignments must match programme, batch, semester and course; multidisciplinary research uses the institutional research-kind scope. Both assigner and mentor must be independent of the accepted team, and the mentor must differ from the assigner by stable person identity. Availability does not establish an institution-wide workload limit: the request still requires expertise/fit and capacity assessments plus a reason. Approved assignment and eligibility capability entries are source contracts, never provisioned by the application. Missing, revoked, expired, unavailable, conflicting or wrong-scope entries deny the request.

The existing trusted loader derives a server-only list of active person IDs from the already validated institutional identity authority. No new provider is installed. The command reloads trusted identity, workspace, roster, academic masters and review authority twice; source/identity/active-person fingerprints must agree before the existing atomic workspace CAS and audit insert. It appends the initial existing-shape assignment with mentor/by actor references, assessment fields, basis and a source snapshot bound to the exact first review, submission digest, team and authority references. The immutable proposal, frozen team, first-review decision and main SUBMITTED state remain unchanged. No ROUTING_CONFIRMED record, execution activity, consultation completion, final approval or finance commitment is manufactured.

This increment handles the first request only. Any existing assignment, including a historical one, requires a future controlled replacement/withdrawal step; no history is overwritten or implicitly renewed. The request is not yet consumable by the legacy acceptance functions, whose legacy routing basis deliberately does not match institutional requests. The next increment will add controlled mentor responses with fresh authorization/source checks.

## Adjacent protection and privacy

The shared team extension blocks generic demo assign/respond/withdraw mentor commands for institutional team cases. Existing individual mentor workflows continue unchanged. Student workspace projections receive only assignment ID, version, mentor actor and state; private capacity/fit/reason, source snapshots, stable person IDs and bindings remain server-side. Dedicated command results also contain only versioned request references and non-execution status. The existing structured INTAKE_MENTOR_ASSIGNMENT audit format is reused with a reason reference; narrative, capacity and mentor person identity are not copied into audit metadata.

No browser mentor controls or real notification delivery are added in this backend increment. The institutional runtime remains disabled with no approved providers. Public Site audience and owner-authenticated workspace API access are preserved. Dashboard → Module Overview → Detailed Process remains unchanged. Semester progression and full demonstration data remain parked; E-Digital Nepal MIS and future LMS boundaries are unchanged.
