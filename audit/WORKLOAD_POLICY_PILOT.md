# Isolated workload policy definition validator

Status: definitions validated with fictional fixtures only; live policy defaults remain frozen, empty and disabled. No import in live routes, engine or UI. G16 stays open and human UI stage remains 107.

`server/workload-policy-pilot.mjs` reuses the existing timestamp utility and checks trusted configuration, stable scoped identifiers and an active-person directory. It is not an identity loader, permission check, enrolment reconciliation, policy approval workflow or student decision engine. A server must independently establish trustworthy inputs before any future integration.

The initial bounded definition contract supports exact institution/workspace/programme/semester/course/activity-type/student-role scopes only. No wildcard, global inheritance, inferred priority or automatic most-restrictive rule is supported. Conflicting same-scope/measure effective periods return review-required instead of choosing a rule. Different measures are separate definitions. Expired, draft/revoked or currently unauthorized definitions produce no current candidate. Disabled configuration always yields no candidates. Validation success is explicitly capability-only and VALIDATED_ONLY; it is not live enablement.

Measures are concurrent activity counts or assigned tasks in current activities. Thresholds must be explicitly supplied positive safe integers; no real institutional value is assumed. Definitions must explicitly name applicable approved-work states, CURRENT_COMMITMENTS, exclusion of paused/proposal work, and person/activity or person/task deduplication. This describes the current bounded prototype baseline. Hours, weighted effort, scheduled date-overlap windows, broader scope/role merging, alternative pause/proposal treatment, and exceptions need separately approved extensions; the validator rejects unsupported choices rather than guessing. It does not calculate any measure or apply a threshold.

Each definition identifies a versioned exact scoped authority and records requester plus independent approver/reference/time. Approved decisions require active directory entries, approval within authority validity and no requester self-approval. Version, effective period and revocation are checked; candidate validity is capped by both policy and authority. The active-person directory and authority catalogue are trusted inputs, not institutional evidence created by this helper. Reassignment, exception authorization and history storage are not implemented.

`check-workload-policy-pilot.mjs` covers disabled/frozen defaults, exact scope, unsupported measures/counting windows, explicit thresholds, modes, independent approval, version/effective-time/revocation, overlap review, malformed definitions, inactive people and detached responses. Every numeric threshold is fictional test data. Existing read-only project-workload checks and TypeScript pass; build is checked with the source checkpoint. No warning, restriction, new-assignment denial, progression decision, grade or inactivity label results from this work.

Next: test exact policy-to-record scope matching and evidence/completeness requirements in isolation before any calculation or warning. Real MIS mapping, approved thresholds/modes/exceptions, protected policy administration and browser/institutional acceptance remain pending. Semester/year progression and full demonstration data stay deferred.

## Isolated policy-to-record matching checkpoint

`matchWorkloadPolicyRecordsPilot` reuses the definition validator; disabled configuration returns no matches. Enabled fictional configurations require an active stable subject and exact programme/semester/course/activity-type/role scope. Current approved candidate definitions must match that exact scope. No wildcard, inferred enrolment or priority selection is introduced.

The proposed mapping contract requires a scoped, person-bound completeness assertion with a source ID/version, capture time and explicit expiry. It must be server-loaded from an authoritative reconciliation; the helper cannot verify truth merely because a caller supplied complete=true. This checkpoint does not connect to MIS/LMS or adapt the live prototype's fixed demo records into authoritative institutional mappings. Missing/incomplete/future/expired coverage returns review-required. An empty record set is meaningful only with that trusted complete coverage assertion. No matching policy returns NO_MATCHING_POLICY, not permission or eligibility.

Mapped activity/task references must match subject, exact scope and source version; only allowed policy states with active control and unresolved participation are matched. Proposals, paused/cancelled work and resolved/history states are excluded. Identical record copies deduplicate; conflicting versions or multiple mappings to the same commitment require review. Every task requires a consistent mapped activity parent; inconsistent parent state/control/outcome is rejected. Results contain definition IDs/versions, measure and selected record IDs/versions plus context expiry. They contain no actual count, threshold comparison, warning, blocking or eligibility outcome. Response mutation cannot change inputs.

`check-workload-policy-matching.mjs` covers exact matching, freshness/completeness, empty versus unknown coverage, duplicate/conflicting units, parent consistency, cross-scope/person/version denial, inactive subjects, definition conflicts, excluded states, disabled defaults and minimal detached results. Existing definition and live read-only summary checks and TypeScript pass; build is checked in the source checkpoint. All data are fictional. Browser/institutional acceptance and approved policy/exception rules remain pending. Next: one isolated calculation over these matched references, clearly labelled counterfactual, before any warning/enforcement proposal. No live activation; progression and full dataset remain deferred.

## Isolated calculation checkpoint

`calculateWorkloadPolicyPilot` calls the exact matcher afresh and counts its already deduplicated references per approved fictional definition. It compares each count with the explicitly configured threshold as BELOW, AT or ABOVE. Equality is a separate boundary case; it is not treated as exceeding a threshold. Activity and assigned-task measures remain distinct and are never combined into a score or inferred hours.

A valid complete empty scoped snapshot yields known zero. Invalid, incomplete, expired, conflicting or inconsistent mappings yield UNKNOWN with review-required and no numeric results. Disabled defaults yield DISABLED; absence of a current matching policy yields NOT_CONFIGURED. Neither means zero, permission or ineligibility. These results are capability-only CALCULATED_ONLY and carry source/configuration versions, selected reference provenance and the mapping/policy expiry bound. They are not stored historical decisions or a production warning/enforcement engine.

WARN and ENFORCE values in the definition fixtures do not trigger behaviour; calculation returns neither mode, eligibility nor allowed/blocked/warning fields. No live routes, dashboards, notifications, assignments, grade, progression, record count, policy configuration or enrolment was changed. The live read-only summary remains independent of this pilot.

`check-workload-policy-calculation.mjs` verifies actual reference counts and the three comparison boundaries, known zero/unknown distinctions, disabled/not-configured outputs, identical duplicate suppression, exclusions, parent consistency, stale/conflicting mappings, detached results and absence of decision fields. Definition/matching/live-summary regressions and TypeScript pass; build is verified at the source checkpoint. All thresholds and records remain fictional.
