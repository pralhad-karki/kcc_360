# Club-member volunteer applications — Stage 145

Implemented a controlled application opening from the existing club event Overview and a member-facing opening/application card in Clubs. Organizers review and explicitly confirm the current position draft, an inclusive closing date in Nepal time (today through the planned start date), and an opening reason. Opening freezes the exact draft positions and source binding. It does not enrol students, create tasks, approve a budget or send recruitment notices. No reopening/amendment workflow is inferred in this first increment.

The current club/event organizer authority is reused for opening. Fresh current approved ordinary plan/event linkage and active club are required. Existing draft version, duplicate opening, unsupported fields, changed source and invalid deadline fail closed. The position draft becomes OPEN and cannot be edited through the draft-save command. Application availability also depends on APPROVED event state and current source binding; cancellation, postponement, suspension, plan/owner/mentor changes or start of execution block new applications.

Initial applicants must have one unended ACTIVE general membership record in the organizing club and a known prototype account. Pending/withdrawn/duplicate memberships and other-club/nonmembers are denied. Executives qualify through active general membership, not appointment alone. The prototype supports one pending position choice per student per opening, with explicit contribution statement and confirmation. This is the bounded initial interaction, not a university eligibility rule; a student can withdraw and reapply while the window is open. Selection and capacity enforcement occur in the next increment; applications do not reserve slots.

Each application is resolved from the authenticated current actor, not a supplied student ID. Expected opening and own application revisions reject stale/replayed requests. Reapplication retains prior history and increments revision. Own pending withdrawal remains possible after a deadline, source change or membership exit; it does not withdraw another person's record or alter event participation. Selected/closed application outcomes are not implemented by these commands.

Three explicit commands use the existing shared endpoint, field allowlists, workspace CAS and atomic audit path: openClubVolunteerApplications, applyClubVolunteerPosition and withdrawClubVolunteerApplication. No route, SQL table or role is added. The narrowly scoped command preservation helper allows only the reviewed recruitment commands; other command entries remain compared with HEAD.

The server supplies a separate minimal clubVolunteerOpenings projection to eligible club members, even if they cannot access the event workspace. It contains published position snapshot, closing date and only the current actor's latest application. It does not reveal the event's private tasks, other applications, source proof, opening reason or draft histories. Existing internal organizer/assigned mentor/Student Affairs readers retain their reviewed event access; ordinary project viewers have internal opening/application fields stripped. Former applicants retain their own application reference/view without wider project access. The Clubs card and forms escape display content. All historical event rosters remain unchanged, including legacy active-member copying.

Evidence: check-club-volunteer-applications.mjs executes the actual shared engine with an approved club/plan/event fixture and frozen draft. It tests organizer-only explicit opening, dates and frozen versions, eligible member discovery without project visibility or enrolment, malformed/expired/source-change/replay/forged-field denial, private projections, own withdrawal/reapplication and retained history, and actual Clubs rendering. The fixture first reconciles existing notifications after simulated source changes so notification housekeeping is not mistaken for application mutation.
