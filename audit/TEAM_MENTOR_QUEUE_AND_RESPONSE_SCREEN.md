# Stage 174 — Scoped mentor queue and response screen

## Essential change and impact

Expose existing institutional team mentor requests and responses through the current Dashboard → Activity Intake overview → assignment detail flow. Add read-only `readIntakeTeamMentorQueue` and `readIntakeTeamMentorStatus` commands to the existing dedicated dispatcher on the authenticated workspace endpoint. A browser-only extension consumes those projections and calls the already implemented `respondIntakeTeamMentor` command. No SQL migration, module, route, engine command permission, role grant, identity provider or real institutional activation is added.

The current verified active assigned mentor and original assignment authority can see a current assignment. A first reviewer, final approver, student, unrelated staff member or broad demo-role label alone has no access to this projection. The server reuses the current reviewed-team validator and mentor source-snapshot validator: frozen submission/team, review, explicit assigner authority, mentor eligibility, verified identity mappings, active people, scope and source basis must still match. Withdrawn, changed, revoked, unavailable, malformed or expired-source records disappear from the queue and cannot be opened. Current assigned mentors may respond only while the latest unique assignment is REQUESTED without response/withdrawal. Completed acceptance/reassignment responses appear read-only after validating the response identity, state, reason, declaration and time.

Reads load trusted sources twice, compare full source/workspace/identity/active-person fingerprints and projection equality, and never persist records or audit rows. The bounded queue returns at most 20 summary rows with pagination. Fresh details include only proposal fields required for supervision, confirmed student IDs/names/lead marker, expertise/fit and the separate consultation-required flag. Private capacity assessments, original assignment reason, source records/bindings, stable person identities and financial data are omitted. Recorded response feedback is visible only within the freshly authorized mentor/assigner view. Existing minimal student assignment summaries remain unchanged.

The dashboard links to the existing module overview. Assignment detail is fetched afresh on opening; the client validates exact assignment, submission, review, actor and workspace references. The response form requires an explicit choice and reason; acceptance requires the supervision/conflict declaration. Assigner and completed-state views contain no response form. All displayed text is escaped. Saving uses the existing version-bound response command; minimal command responses cannot replace workspace data. Only a fresh full workspace for the unchanged account can be applied. Conflicts and uncertain saves require status refresh without automatic replay. Snapshot, account, generation, cache, modal-marker and lock-ownership guards reject late/stale actions; an already committed save still synchronizes if the dialog closes during the request.

The browser extension wraps the existing refresh/reset/dashboard/intake hooks and is copied by the existing workspace generator; it is not loaded into the server engine. Failed/disabled capability discovery performs no extra mentor reads. The institutional runtime remains disabled with no approved providers; ordinary hosted demo accounts do not gain institutional queue access. Existing individual mentor screens, other team screens, Site audience and API owner authentication remain unchanged. Semester progression and full demonstration data remain parked, and MIS/future LMS boundaries remain intact.
