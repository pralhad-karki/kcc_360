# Isolated Excel planning-reader feasibility

Status: offline conversion and existing-validator bridge tested. Direct workbook import in the deployed application is NOT implemented. G15 remains open. Human UI stage remains 105.

`scripts/read-plan-xlsx.py` uses the available openpyxl parser for isolated conversion in the development environment. No Python service, application dependency, HTTP endpoint, attachment storage or browser input was added. A compatible browser/Worker parser and dependency review are still needed before wiring direct .xlsx input into existing forms. Do not copy this Python helper into a Worker route or claim the current CSV chooser accepts Excel.

The caller supplies the exact current academic or club import columns. A workbook with multiple worksheets requires explicit worksheet choice; sheets are never silently merged. The selected sheet must be visible, unmerged and without hidden rows/columns. Header order is exact, at most 50 data rows, 40 columns, 1 MB compressed input, 4 MB expanded archive and 30,000 converted CSV characters. Excess formatting beyond the supported range is rejected rather than silently clipped. Archive names, expansion, macros, embedded objects, external-link parts and XML entity declarations receive bounded rejection checks. These are format restrictions, not malware scanning or production security certification.

Formulas, spreadsheet error cells, hyperlinks and boolean cells are unsupported. Identifiers must be text cells so leading-zero formatting is not guessed. Blank cells remain empty. String values are preserved and quoted through the standard CSV writer. Numeric values are literal numbers, not displayed workbook formatting. Calendar date cells are converted to ISO YYYY-MM-DD only in start/end/reportDue, with no time of day and dates restricted to 1970–2100 for this pilot. Existing CSV date rules remain authoritative for imported text. Both Excel 1900 and 1904 date systems are exercised through the parser. Unsupported cells produce an explicit error; there is no formula evaluation or inferred academic mapping.

Validation evidence:

- `python check-plan-xlsx-reader.py`: literal/quoted/newline preservation, ordinary dates and both epochs, exact headers, explicit sheet choice, hidden/merged layout denial, unsupported cells, limits and malformed/unsafe archives.
- `node check-plan-xlsx-bridge.mjs`: temporary fictional workbooks are created entirely in memory, converted and passed to unchanged academic/club CSV preview commands. Invalid date rows remain reported, explicit valid-row confirmation remains necessary, duplicate confirmation is idempotent, and imports retain draft approval gates. No live workspace or full sample population.
- Existing `check-plan-imports.mjs` and `check-club-imports.mjs` remain passing.

No .xls/.xlsm support, recurrence engine, new approval, roster authority or progression behaviour was added. ## Stage 106 — Direct .xlsx preparation connected

Academic and club CSV import forms now accept .xlsx as well as CSV. A lazy-loaded controller sends local file bytes to a dedicated worker using the exact pinned local SheetJS build and exact copied pure adapter. Workbook bytes are not uploaded. Multi-sheet workbooks require explicit worksheet selection; single-sheet workbooks are loaded directly. Conversion populates the editable CSV text area only. The operator still supplies a source reference, runs existing server preview and explicitly confirms valid rows. CSV and server business validation remain authoritative; no routes, schema, grants, budgets or approval states were added.

The reader has a 1 MB input limit, existing 50-row/30,000-character output limits, supported layout/date/text restrictions, and a five-second worker timeout per task. Cancel terminates the worker; modal close/replacement cancels pending preparation. A late worker cannot stop or overwrite a newer task. Errors, cancellation, manual text edits, file replacement or a replaced form preserve current text. Unsupported-worker browsers can continue with CSV. Selected names and result/error messages use textContent; they are not injected HTML. Files remain in tab memory and are released after conversion/cancellation; no attachment library or sample dataset is populated. Local vendor licence is shipped with the assets; no external runtime CDN is required.
