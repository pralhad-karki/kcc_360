# Club recruitment audience review and preview — Stage 143

Review of current working code confirmed that ordinary clubEvent creates an APPROVED event from an active club's latest approved annual-plan row and copies every ACTIVE club member into project.members. Authorized special club activities also copy active members at conversion. Existing task/assessment/portfolio flows use that roster. Neither path currently implements event-specific volunteer positions, applications, selection or domain-lead delegation. Membership applications and mentor/Student Affairs governance already work separately.

Minimum safe next step implemented: a read-only Initial volunteer recruitment audience panel appended to existing ordinary club event overview, via one browser extension file loaded after the existing app. No core event creation, roster, command, authority, SQL schema, API route or completed workflow changes. It is visible only within existing event access to club managers, the active-member event owner, assigned club mentor and Student Affairs. Other readers receive no panel or recipient projection.

Audience uses only the organizing club's ACTIVE general membership records, independently of project.members and other clubs. Leadership alone does not qualify; an executive who also has active general membership is included. Pending/rejected/withdrawn memberships and nonmembers do not qualify. Pending exits continue under existing membership authorization rules. Unknown demo identities, ended-but-active records and duplicate ACTIVE memberships are excluded and counted for review. Current active club, eligible event state, no cancellation/postponement and exact current approved plan/item/event linkage are required. Special-activity source mapping is deliberately pending, rather than inferred.

This is a preview of current prototype records, not an institutional identity/MIS authorization boundary or notification send service. It displays recipient references/names already within those roles' existing club register access, escapes output and performs no persistence or network operation. No initial notice, volunteer application, selection, enrolment or achievement is created. The panel explicitly explains that legacy events still copy active members and that event membership must become separate from recruitment in the future path.

Essentiality/impact/complexity: exposes the approved initial audience rule for review while preserving working events and downstream tasks/evaluation/finance. The bounded read-only screen has low implementation complexity. Changing event rosters now would affect participant visibility, task assignment and evaluation before a selection path exists; therefore that behavioral change remains part of the later opt-in recruitment conversion, without rewriting historical events.

Evidence: check-club-recruitment-preview.cjs creates a club, approves membership/leadership/annual plan and generates an event through actual prototype commands, then checks organizing-club-only active recipients, role denials, leadership-only/nonmember exclusion, inconsistent-record review, cancelled/suspended/stale linkage denial, escaping, no mutation and unchanged event roster. Existing club, membership and role-dashboard checks plus TypeScript are rerun. Browser acceptance remains Not run; the previous full baseline is Stage 142's 126 suites, not a new Stage 143 baseline.

Next: define event-specific task domains and volunteer positions/capacities under the existing club event; then connect club-member-only applications and selection before enabling a new recruitment roster path. Preserve existing task/evaluation/achievement/portfolio services. No automatic all-college broadcast. Semester/year progression and full demonstration dataset remain deferred.
