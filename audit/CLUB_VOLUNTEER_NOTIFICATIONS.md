# Targeted club volunteer in-app notices — Stage 147

Connected recruitment-opening and application-review notice sources to the existing notification actions, recipient access, candidate generation and persistent reconciliation. One extension file wraps the existing source/access functions; the original notification module, commands, policies, routes and database schema are unchanged. Existing workflow commands reconcile the new notices in the same shared save, and explicit notification refresh also reconciles them. No background timer, push, email or SMS transport is added.

Opening notices target only known accounts with one unended ACTIVE general membership in the organizing club, while the approved opening source is current and its Nepal closing date has not passed. A leadership appointment alone grants no audience access; active general members who are executives are still included. Other clubs, pending/withdrawn/ambiguous membership records and nonmembers are excluded. Once someone has an application record for the opening, the opportunity notice resolves; withdrawal does not repeatedly advertise the same opening to that applicant. The existing Clubs card still permits eligible reapplication.

Review-feedback notices target only the exact applicant with the latest current review/application revision (selected, not selected or returned for review). Titles contain no contribution statement, feedback reason, applicant list or reviewer identity. The applicant opens their own limited Clubs application view to read feedback. A former club member with an existing current reviewed application may retain their own decision notice; this does not broaden the initial recruitment audience or grant general event access.

All new notices are optional INFORMATION sources with no due date or escalation chain. Thus an approved generic CLUB reminder policy cannot escalate voluntary opportunities/decisions to faculty, Student Affairs or administrators. Existing routine-notice preferences still apply. Reading a notice neither submits an application nor accepts, selects or enrols anyone.

Deterministic source/version/recipient IDs reuse the current inbox deduplication and read-state behavior. Source/eligibility loss, application, expiry, suspension or corrected decisions resolve old notice rows. A corrected review creates the notice for the new application revision; prior stored rows/history remain. Access is rechecked against current source/version before read/visibility. Old rows whose source is no longer relevant are not exposed as active or actionable messages.

The limited opening projection now includes sourceCurrent for recipient-side access validation. In shared mode the browser derives only the current actor's notice sources from that minimal projection, rather than requiring a private event in db.projects. Server reconciliation continues to derive from full trusted workspace data. This lets a general member outside the event roster see/open a notice without gaining access to private event tasks, peers or draft history. Existing Open source navigation uses Clubs and the application card; no new route is introduced.

Evidence: check-club-volunteer-notifications.mjs executes approved club/event/draft/opening/application/review commands through the actual engine. It tests organizing-club-only opening recipients even under an approved escalation-policy fixture, optional information-only notices, duplicate/read preservation, recipient visibility/source navigation from projected data without event access, revocation/expiry/suspension resolution, generic private decision notice, version correction, withdrawal and unchanged roster/tasks. The full local baseline passed 131/131 scripts in 61.381 seconds (AUTOMATED_BASELINE_STAGE147.json), including existing notification tests; TypeScript/diff checks passed. Browser/keyboard/institutional acceptance remains Not run. Test fixture policies/data are local only, not adopted institutional rules or a populated demonstration dataset.

Essentiality/impact/complexity: adds the missing targeted communication through the existing inbox and navigation. Moderate complexity is needed to keep current source validation and non-enrolled applicant privacy aligned. No new user module, role, notification group or external delivery service is introduced.
