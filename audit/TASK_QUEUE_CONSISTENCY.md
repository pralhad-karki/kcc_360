# Stage 154 — Task and mentor-review queue consistency

Review finding: the existing task-review source used mapped/SUBMITTED state and execution stage, but omitted several checks enforced by reviewTaskWork: active assignee, independent current mentor, matching submission student/mapping and an existing evidence reference. Both ordinary assignment and review sources also needed the existing club/internship execution-availability guard. Stored task notices used broad project-read access, so a stale review could remain visible until reconciliation.

Minimum change: one task queue extension loaded after existing notifications in the current browser/server preparation chain. It filters existing task:/task-review: source actions and checks their stored notification access against current workflow data. The original notification module, task commands, grading, roles, SQL schema, API routes and policy timing remain unchanged. No new navigation module or queue storage is introduced.

Review source eligibility requires current active execution, active assignee, mapped submitted task, independent assigned mentor, latest positive submission version, matching student/mapping and an existing evidence reference. Evidence need not already be verified for a review to be queued: the mentor may return or partially assess work; VERIFIED still requires evidence verification in the existing command. Assignment queues retain APPROVED preparation responsibilities and original return/correction version rules, but stop when their current source cannot execute. Submitted work is routed to mentor review rather than the student's assignment queue.

Stored task notices must still match source/task identity, recipient, submission/assignment version, deadline and canonical notification identity. Current primary recipients and the original approved escalation chain are preserved. Stale mentor, assignee, mapping, version, deadline, outcome or suspended-source notices are hidden before persistence/reconciliation; existing reconciliation marks obsolete rows resolved and retains delivery/read/history records. Valid current read receipts and deduplication remain intact. Optional verified-completion notices and all unrelated notification sources remain in their original workflows.

Dashboard and Action Centre use these same filtered notification-derived actions. Existing source navigation rechecks current assignment; detailed mutation commands retain their independent validations. No staff role gains the right to review merely because it can read a project or receive an escalation. No background timer, email or SMS transport is activated.

Validation: check-task-queue-consistency.mjs creates a domain task through the actual selected-volunteer/handoff workflow, starts an Event, submits work/evidence and tests current mentor review. It covers inactive/resolved assignee, mismatched assignee/student/mapping, absent evidence, self-review, mentor change, suspension/postponement/stage changes, stale stored-notice access/acknowledgment, receipt/dedup preservation, approved overdue/escalation recipients, return/correction and resubmission versions, independent evidence/task verification, optional completion and retained resolved history. Full evidence is AUTOMATED_BASELINE_STAGE154.json. These are local model/controller and projected-record fixtures, not browser or institutional acceptance.
