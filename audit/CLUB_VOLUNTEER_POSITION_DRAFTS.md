# Club event volunteer position drafts — Stage 144

Implemented editable draft task domains, volunteer position titles, capacities and expected contributions in the existing club event Overview. The form starts blank, allows up to ten position definitions and repeats domains where needed. Capacity 1–999 and field/row length bounds are prototype input limits, not institutional team-size or attendance rules. No demonstration dataset is populated.

The existing organizer authority governs editing: current club manager or an event owner with active general membership. The event must be APPROVED, belong to an ACTIVE club, retain its current approved ordinary plan/item linkage, have no cancelled/postponed control or resolved participant outcome, and have no already-open recruitment plan. Mentor and Student Affairs may read the draft within existing event scope; they gain no edit or invented approval authority. Started events are not eligible for this initial drafting step. Special-activity recruitment mapping remains pending.

One explicit saved command, saveClubRecruitmentPlan, uses the existing workspace endpoint, form allowlist, authenticated account/context and workspace CAS/atomic audit transaction. It requires the current draft version, validates every used row, rejects duplicate domain/position pairs and malformed capacities, and saves a new DRAFT version with source references, author, time and revision reason. Earlier versions are retained. Event roster, existing tasks, budgets, attendance, evaluation, portfolios and existing approvals are unchanged. No application window, applicant, selection, task delegation or recruitment notification is created.

The browser extension and its existing audience-preview dependency are included in the established generated engine source list. The engine projection removes internal recruitment drafts from other project viewers; ordinary students cannot inspect unpublished position versions via the shared API. A narrowly scoped preservation helper allows exactly the reviewed save command addition and compares every other command with HEAD. Existing pilot preservation assertions now use that helper only for commands.json; all their other protected files retain exact comparisons. The older discussion guard also permits only this one reviewed addition. Existing service/route/SQL definitions are unchanged.
