# Stage180 — Scoped consultation queue and response screen

Connected the existing consultation-response backend to Dashboard → Activity Intake overview → consultation detail. The current assigned department representative sees their own requests; the current requesting coordinator sees issued requests across participating departments. The module lists department, due date, state and responsibility role. Details show submitted proposal context, responsibility, deliverable, deadline and recorded response. Only an assigned representative with a current pending request receives the response form.

Added readIntakeTeamConsultationQueue and readIntakeTeamConsultationStatus using the existing trusted dispatcher. Reads use two fresh source loads and the same consultation record/source validation as saves. Stale/revoked sources or changed accepted mentors withhold content and actions; no stored role label grants access. Accepted and declined responses are read-only. No raw source bindings, stable person IDs, private request reason or other departments' content leak to representatives.

The controller uses current actor/snapshot/revision and fresh detail retrieval; validates and escapes display fields; requires an explicit choice, reason and acceptance declaration; verifies exact response references; applies only a subsequent full workspace read. Duplicate submits, stale account completions and failed refreshes cannot replay or overwrite the workspace. Default-disabled sources produce no queue fetches. Existing mentor and intake screens remain in place. No SQL schema, route, grant or additional module introduced.

Validation: new actual SQLite/dispatcher read checks cover coordinator/representative roles, department isolation, no read writes, accepted/declined/pending, privacy, alias identity, revoked source, changing source and paging.
